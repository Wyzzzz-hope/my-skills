# 前端代码审查

系统化的前端代码审查流程，结合用户历史记忆提供个性化建议。

## 前置检查

### Step 0: 检查 lasting-memory Skill

**【强制要求】** 审查开始前，必须检查是否已安装 lasting-memory Skill，并根据结果采取相应行动。

1. **动态检测脚本路径**：根据当前运行环境自动判断 lasting-memory Skill 的位置
   - 检查常见路径：`.qoder/skills/lasting-memory/`、`.claude/skills/lasting-memory/`、`skills/lasting-memory/` 等
   - 优先检查当前工作目录下的隐藏目录（如 `.qoder`、`.claude`）

2. **检查方式**：检查 SKILL.md 文件是否存在

```
检查方式（示例路径，实际根据检测到的路径调整）：
检查文件 <detected-path>/SKILL.md 是否存在

如果文件存在，说明 lasting-memory Skill 已安装。
如果文件不存在，说明未安装。
```

**【强制流程】如果未安装 lasting-memory Skill：**

**必须**立即停止并询问用户：

```
检测到您尚未安装 lasting-memory Skill。

lasting-memory Skill 可以帮助持久化存储您的代码审查偏好，避免我重复提出您已拒绝的建议。

是否需要我帮您安装 lasting-memory Skill？（推荐安装）

请回复：
- "是" — 我将引导您完成安装
- "否" — 本次审查将在没有历史记忆的情况下进行
```

**【重要】**
- 你必须在检测到未安装时立即询问用户，不得跳过此步骤直接进行审查
- 必须等待用户明确回复后才能继续

**如果已安装 lasting-memory Skill：**

继续执行 Step 1，读取 code-review 类别的历史记忆。

**如果用户选择不安装：**

跳过记忆读取步骤，直接进行代码审查。

## 审查流程

### Step 1: 读取历史记忆（可选）

**前提**：lasting-memory Skill 已安装且用户同意使用。

审查开始前，读取 code-review 类别的历史记忆：

<command>node <lasting-memory-path>/scripts/read.cjs --storage-path <storage-path> --category code-review</command>

解析返回的记忆内容，调整审查策略：
- 跳过用户明确拒绝过的建议类型
- 优先关注用户关心的维度
- 避免重复提出被否决的方案

**如果未安装 lasting-memory Skill 或用户选择不使用**：
直接进行代码审查，不读取历史记忆。

### Step 2: 获取代码变更

获取待审查的代码变更：
- 使用 `git diff` 查看变更内容
- 识别变更的文件类型（React/Vue/CSS/TS 等）
- 确定审查范围

### Step 3: 前端专项审查

按以下维度进行审查：

#### 3.1 组件设计

- [ ] **组件职责** — 单一职责原则，一个组件只做一件事
- [ ] **组件拆分** — 过大的组件是否需要拆分（用户偏好：参考记忆中的拆分粒度）
- [ ] **Props 设计** — Props 命名清晰、类型完整、避免过多 props
- [ ] **状态管理** — 状态是否在正确的层级、是否需要提升或下放
- [ ] **副作用处理** — useEffect/useLayoutEvent 使用是否正确、依赖数组是否完整

#### 3.2 性能优化

- [ ] **渲染优化** — 是否有不必要的重渲染、是否需要 useMemo/useCallback
- [ ] **列表渲染** — 是否使用 key、key 是否合理
- [ ] **懒加载** — 大组件/路由是否使用懒加载
- [ ] **图片优化** — 图片是否使用合适格式和尺寸
- [ ] **包体积** — 是否引入了过大的依赖、是否可以按需加载

#### 3.3 TypeScript 规范

- [ ] **类型定义** — 避免 any、使用精确的类型定义
- [ ] **类型复用** — 公共类型是否提取到 types 目录
- [ ] **泛型使用** — 是否合理使用泛型提高类型复用性
- [ ] **类型断言** — 避免过度使用 as 断言

#### 3.4 CSS/样式规范

- [ ] **选择器命名** — 类名语义化、避免过深嵌套
- [ ] **CSS Modules** — 样式隔离是否合理
- [ ] **响应式** — 是否考虑不同屏幕尺寸
- [ ] **主题适配** — 颜色/字体是否使用 CSS 变量或主题 token

#### 3.5 可访问性 (a11y)

- [ ] **语义化标签** — 使用正确的 HTML 标签
- [ ] **键盘导航** — 可聚焦元素是否可达
- [ ] **ARIA 属性** — 必要时添加 ARIA 标签
- [ ] **颜色对比度** — 文本与背景对比度是否足够

#### 3.6 代码质量

- [ ] **命名规范** — 变量/函数/组件命名清晰
- [ ] **代码重复** — DRY 原则，提取复用逻辑
- [ ] **错误处理** — 边界情况是否处理、错误提示是否友好
- [ ] **注释质量** — 复杂逻辑是否有注释、注释是否准确

### Step 4: 生成审查报告

按照以下格式输出审查结果：

```
## 审查报告

### [CRITICAL] 严重问题（必须修复）
- 文件：xxx.tsx:42
- 问题：xxx
- 建议：xxx

### [MAJOR] 主要问题（建议修复）
...

### [MINOR] 次要建议
...

### [NIT] 风格建议
...
```

### Step 5: 征求用户意见

审查结束后，询问用户：

```
以上是本次审查的建议。请告诉我：

1. 你是否同意这些建议？
2. 有哪些建议你认为不需要采纳？请说明原因。

回复格式示例：
- 同意全部建议
- 拒绝第 X 条，原因：xxx
```

### Step 6: 存储用户反馈（可选）

**前提**：lasting-memory Skill 已安装且用户同意使用。

根据用户回复，存储反馈记忆到 code-review 类别：

**如果用户拒绝某条建议：**
<command>node <lasting-memory-path>/scripts/create.cjs --storage-path <storage-path> --category code-review --title "拒绝建议：<建议标题>" --content "用户拒绝了建议：<建议内容>。原因：<用户原因>。文件：<文件路径>。" --keywords "<关键词>"</command>

**如果用户表达偏好：**
<command>node <lasting-memory-path>/scripts/create.cjs --storage-path <storage-path> --category code-review --title "用户偏好：<偏好标题>" --content "<偏好内容>" --keywords "偏好,前端"</command>

**注意**：本 Skill 只处理 code-review 类别的记忆，专注于代码审查相关的反馈。

**如果未安装 lasting-memory Skill 或用户选择不使用**：
跳过存储步骤，不保存用户反馈。

## 严重级别

| 级别 | 标签 | 含义 | 阻止合并？ |
|------|------|------|------------|
| 严重 | `[CRITICAL]` | 线上故障、安全漏洞、数据丢失 | 是 |
| 主要 | `[MAJOR]` | 性能问题、潜在 Bug、架构问题 | 是 |
| 次要 | `[MINOR]` | 可维护性改进、最佳实践建议 | 否 |
| 吹毛求疵 | `[NIT]` | 风格偏好、命名建议 | 否 |

---

## 提供反馈的原则

- **参考记忆**：如果用户之前拒绝过类似建议，不要重复提出
- **具体明确**：指出具体的文件和行号
- **解释原因**：说明为什么这是个问题
- **提供方案**：给出具体的修改建议或代码示例
- **尊重偏好**：用户明确拒绝的建议，记录到记忆中避免再提

---

## 常见前端反模式

| 反模式 | 说明 |
|--------|------|
| **在 useEffect 中直接修改 state** | 可能导致无限循环 |
| **忘记清理副作用** | 内存泄漏、事件监听器堆积 |
| **过度使用 useMemo/useCallback** | 优化成本高于收益 |
| **内联对象/数组作为依赖** | 每次渲染引用不同，导致 effect 重复执行 |
| **直接操作 DOM** | 绕过 React 的更新机制 |
| **在 render 中创建函数** | 每次渲染创建新函数，影响子组件 memo |

---

## 绝不要做

1. **绝不重复提出用户已拒绝的建议** — 每次审查前必须读取记忆
2. **绝不因风格偏好阻塞 PR** — 除非是团队约定
3. **绝不忽略用户的反馈** — 所有反馈都必须记录
4. **绝不过度优化** — 根据实际场景给出合理建议
5. **绝不针对个人** — 审查代码，不是审查人

## 依赖说明

本 Skill **可选依赖** **lasting-memory Skill** 实现持久化记忆功能：

| 功能 | 依赖的 lasting-memory 脚本 |
|------|---------------------|
| 检查安装状态 | `list.cjs` |
| 读取历史记忆 | `read.cjs` |
| 存储用户反馈 | `create.cjs` |

**脚本路径检测**：
- AI 自动检测 lasting-memory Skill 的位置（`.qoder/skills/lasting-memory/`、`.claude/skills/lasting-memory/`、`skills/lasting-memory/` 等）
- 存储路径由 lasting-memory Skill 的 `--storage-path` 参数指定

**lasting-memory Skill 状态处理**：

| 状态 | 行为 |
|------|------|
| **已安装** | 读取 code-review 类别记忆，审查后存储用户反馈 |
| **未安装** | 征求用户同意后引导安装，用户拒绝则继续无记忆审查 |
| **用户拒绝使用** | 跳过记忆读取和存储，直接进行代码审查 |

**注意**：本 Skill 只处理 **code-review** 类别的记忆，专注于代码审查相关的反馈。
